## Analyze

- **Same work, verified.** Three independent implementations agree on all nine reference
  checksums (unit tests) and on all 50 benchmark runs, so the rows compare the same work.
- **HotSpot removes all four temporaries.** With escape analysis on, window 0 allocates 0.0 B/op
  and runs no GC; with `-XX:-DoEscapeAnalysis` the same code allocates 96 B/op (four 24-byte `Vec`
  objects) and is 3.8x slower (2.8 vs 10.7 ns/op). The log lists exactly the four sites (two in
  the loop, one inlined from `Vec.add`, one from `Vec.scale`).
- **Retention defeats it for exactly one object.** Window 100,000 allocates 24.0 B/op: the `c`
  stored in the ring escapes, the other three are still removed (96 B/op without escape analysis).
- **Root causes of the three escaping cases** (each confirmed by a fixed variant that differs only
  in that respect, and by the log):
  - *branch-merge*: two allocations meet at a control-flow join, so the reference can point to
    either object and C2 keeps both (0 `Vec` eliminations logged; 24 B/op with and without escape
    analysis). `-XX:+PrintFlagsFinal` on this JDK 21 build lists no option that changes this.
  - *loop-accumulator*: the accumulator `sum` is a loop-carried value. The log shows the per-step
    `Vec` (line 106) removed but no entry for the `Vec` created inside `add`, which matches the
    measurement: 24 B/op (one object) instead of 48 B/op (two, escape analysis off).
  - *static-store*: storing the reference in a static field makes it reachable from everywhere
    (0 eliminations, 24 B/op). It is also the slowest case (9.29 ns/op); how much of that comes from
    the reference store itself, beyond the allocation, is not measured yet.
- **V8 also removes temporaries, with different limits.** With the constructors written in the
  loop body, TurboFan's escape analysis removes every object (80 to 0 B/op); through `add()` and
  `scale()` 55.9 B/op remain (176 without escape analysis). In the shared workload Node.js
  allocates 48 B/op with escape analysis and 168 B/op without; which objects remain is not
  attributed yet (`--trace-turbo-escape` printed nothing on this release build of Node.js).
- **Young-collection pauses grow with survival, not only with allocation.** Node.js window 0
  allocates about 1.05 MB between scavenges (45.8 scavenges per million operations, about 0.06 ms
  each). With window 100,000 the young generation grows to about 63 MB between scavenges
  (1.5 per million operations) and each scavenge costs about 2.6 ms (76 to 88 ms for 30), because
  the 100,000 live objects must be copied. Fewer pauses, each about 45 times longer: a latency
  spike from a change in object lifetime alone. Java shows the same direction (G1, ms resolution:
  one run: 3 young pauses totalling 5 ms for 480 MB at window 100,000).
- **CPython's cycle collector counts net growth of tracked objects, not allocations.** Window 0
  allocates millions of `Vec` objects and runs 0 collections: each object is freed by reference
  counting as soon as it is dropped. With a window, collections = window / 2,000 (the generation-0
  threshold) per round, independent of the number of operations (2,000,000 ops gave the same 50
  as 1,000,000). Older-generation collections cost about 1.1 to 1.7 ms each against about 0.06 to 0.07 ms
  for a young one, so a growing cache produces occasional millisecond pauses even when nothing is
  garbage.
- **Defects found while building, and their root causes:**
  - A mutation in the log reader (ids not scoped per `<task>`) survived the first test suite.
    Root cause: the fixture's tasks all re-declare their ids, so stale ids never mattered. Fixed
    with a test whose second task uses an id declared only in the first.
  - The first ADR draft said HotSpot writes its per-thread compile logs to the working directory.
    Watching a run showed `hs_c*.log` files in the temp folder instead. Root cause: an assumption
    not checked. The runner now sets `TMP`, `TEMP` and `TMPDIR` to `.tmp/jit/` for that JVM.
  - A Java mutation that removed `Arrays.fill` failed the build at Spotless (unused import), not
    at the tests; the mutation was redone with a call that keeps the import and clears nothing,
    and the tests caught it.

## Control

- **Tests hold the claims in every runtime:** the shared checksums (Java, Python and JavaScript
  suites), behaviour preserved by every fixed variant (`EscapeCasesTest`, 200 seeds, and
  `escape-probe.test.js`, 100 seeds), and 0 vs 24 B/op inside the test JVM
  (`EscapeAnalysisTest`, skipped only if escape analysis or the JIT is switched off).
- **CI gates** (`.github/workflows/ci.yml`): `make bench` exits 3 if any runtime returns a checksum
  other than the spec's; `make escape` exits 3 if a fixed variant allocates 0.5 B/op or more, an
  escaping one allocates less than 23.9 B/op, results disagree, or the log has no eliminated
  `Vec` for a fixed variant. Both print their `RESULT` line as a `::notice` (or `::error`)
  annotation and append their tables to the job summary. The audit step fails on any known
  vulnerability.
- **Mistake-proofing:** the runner rejects any result line with a missing, extra or mistyped
  field; the spec loader validates every value and range; all harnesses reject unknown, repeated
  and out-of-range options; every round must return the same checksum or the harness fails;
  `test_compare.py` fails if an experiment JVM is launched without the heap cap or with a crash
  file, heap dump or temp path outside `.tmp/`; the log reader refuses DTDs and oversized files.
- **Reproducible build:** pinned Maven plugin, npm and action versions (actions by commit SHA),
  Enforcer for JDK and Maven versions, fixed `project.build.outputTimestamp`, `package-lock.json`.
